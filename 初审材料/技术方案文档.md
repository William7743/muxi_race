## 1. 问题定义

赛题要求实现 DeepSeek 风格 MoE 中 pre-routed fused expert GEMM。评测程序按固定
接口调用 `run_kernel`，输入为已按 expert 分组的 token（`stacked_expert_tokens`）、
三份 expert 权重（gate/up/down）、路由元数据（`group_sizes/group_offsets/
group_padded_offsets/group_idx_for_bx`）与路由权重（`routed_expert_weights`），
输出为 `out = (SiLU(x@Wgᵀ) ⊙ (x@Wuᵀ)) @ Wdᵀ ⊙ routed`。

三个正式评测用例（fp16，group 元数据 int32）：

| 用例 | n_experts | d_hidden | d_expert | group_sum(valid) | warmup/iters |
|---|---|---|---|---|---|
| 1 | 16 | 2048 | 8192 | 2272 | 5 / 30 |
| 2 | 32 | 7168 | 2048 | 4544 | 5 / 20 |
| 3 | 64 | 7168 | 2048 | 9088 | 5 / 20 |

**计分**：每用例得分 = 100·s/(1+s)，s = T_baseline/T_kernel；总分为三用例均值。
这意味着优化需要**三用例同时进步**，慢速用例主导失分。

**约束（合规红线）**：GPU 计算算子只能使用 TileLang（不得用 PyTorch 计算、不得
`import_source`/`call_extern` 注入或调用外部设备实现、不得使用异步/流水线语义、
不得跨调用缓存结果、不得使用 mcTlass 等外部库）。本方案全部结论与实现均在上述
约束内。

## 2. 硬件与软件环境

| 组件 | 说明 |
|---|---|
| GPU | MetaX C500（64GB HBM；实测 DRAM 峰值带宽 ≈1.44 TB/s；L2 ≈8 MB；warp = 64 线程） |
| MACA 软件栈 | 3.7.x / 3.8.x（驱动 3.8.30 实测通过） |
| 编译器 | TileLang-MetaX 0.1.x（race 分支，参考 commit ee6db43） |
| 框架 | torch 2.8.0+metax（仅 host 侧张量分配）、Python 3.12 |

关键架构事实（实测）：C500 **没有 cp.async 类异步拷贝指令**，`T.Pipelined`
num_stages≥2 的多缓冲只增加同步开销（详见 §4.2）；全局加载→寄存器→shared 的
同步路径上，硬件记分板允许"先发后等"，这是本方案重叠策略的基础。

## 3. Kernel 总体设计方案（v432 最终形态）

### 3.1 两阶段结构

```
Stage1（fused Gate+Up）:  for each (bx, by) 网格点:
    A = x[block_start:+128, k*64:+64]        （token 块，两次 MMA 共享一次加载）
    Wg = gate_w[e, by*128:+128, k*64:+64]    （gate 权重块）
    gate_acc += A @ Wgᵀ                      （MMA，fp32 累加）
    Wu = up_w[e, by*128:+128, k*64:+64]      （up 权重块，寄存器预取重叠，见 §3.3）
    up_acc  += A @ Wuᵀ
    up_logits[行, by*128:+128] = SiLU(gate_acc) ⊙ up_acc   （仅有效行）
Stage2（Down）:            for each (bx, by) 网格点:
    out_acc += up_logits[...] @ down_wᵀ
    out[行] = out_acc ⊙ routed[row]
```

Stage1/Stage2 同一次 `run_kernel` 内先后 launch（默认流天然串行，Stage2 依赖
Stage1 的 `up_logits` workspace，无需额外同步）。

### 3.2 分块与网格（per-shape 特化）

| 参数 | Stage1 | Stage2 |
|---|---|---|
| M 块 bt（token） | 128（与评测方 `group_idx_for_bx` 预计算粒度一致） | 128 |
| K 块 bh / bk | 64 | 64 |
| N 块 be / bn | 128 | 128（Stage2 权重维度为 hidden） | 
| threads | 256 | 256 |
| MMA warp 策略 | Square | Square |

网格尺寸：Stage1 = `num_blocks_m × d_expert/128`，Stage2 = `num_blocks_m ×
d_hidden/128`。expert 由 `group_idx_for_bx[bx]` 查表获得；块内有效行数
`actual_rows = clip(group_size − token_offset, 0, 128)`，`actual_rows == 0` 的
块直接空转返回。

### 3.3 关键机制

**(a) A 操作数 shared 化**。早期实现把 A（token 块）放入 fragment，每线程持有
分散元素，LDS→寄存器搬运成为 MMA 供给瓶颈（实测纯 GEMM 仅 26.8 TFLOPS）。
改为 `T.alloc_shared` 后 MMA 直接以 shared 为操作数，**87 TFLOPS（3.2×）**。
此外 gate/up 两次 MMA 共享同一份 A 块，A 的全局加载次数减半。

**(b) Stage1 gate/up 记分板重叠（up 寄存器预取）**。串行循环的原始顺序为
copy(A) → copy(Wg) → MMA(gate) → copy(Wu) → MMA(up)，两次权重拷贝与两次 MMA
完全串行。v432 将 up 权重块提前加载到 **fragment 寄存器**（`up_prefetch`），
在 gate MMA 执行期间完成全局加载，gate MMA 结束后仅做寄存器→shared 的短途搬运
再执行 up MMA。该重叠不使用任何硬件异步指令，依赖加载指令的记分板机制（发射后
延迟等待），因此完全符合"禁用异步"的合规边界。实测相对串行版提升约 0.5-1%
（hidden=7168 档），case1 在分派全开后获益 -6.8%。

**(c) 编译 pass 开关组合**（均经三 case A/B 验证）：
- `tl.enable_fast_math`（全部 4 个 kernel）：-0.5~1%，三 case 一致正收益；
- `tl.enable_lower_ldgstg_predicated`（stage1_prefetch / stage2_fast）：谓词
  化全局加载 lowering，正收益；
- `tl.disable_safe_memory_legalize` + `tl.disable_vectorize_256`（仅
  stage2_fast）：实测与默认 lowering 逐字节等价（对拍 bad=0）后启用。
- `TL_DISABLE_WARP_SPECIALIZED`：当前 MACA 后端必须关闭（否则无法编译）。

**(d) 访存合并**。全部权重 `T.copy` 指定 `coalesced_width=8`（16 字节/线程），
实测比默认合并宽度快约 0.3%（过大宽度会越界，已实测排除）。

**(e) Stage2 满块快路径 epilogue**。`actual_rows == bt1` 的满块走无谓词写回，
仅尾块保留 `i < actual_rows` 谓词；padding 行显式写 0，保证 `out` 语义与参考
实现一致。

**(f) MMA k_pack**。hidden ≥ 7000 的用例（case2/3）Stage1 使用 `k_pack=2`
（单条 MMA 打包 2×16 的 K 切片），case1 保持 1；均经扫描验证。

**(h) Stage2 手写同步调度与 MMA swizzle 布局（v469 新增）**。Stage2 原本的
`T.Pipelined(num_stages=1)`（与官方模板一致的退化形态）会被编译器展开为带动态边界
谓词的调度。v469 用纯同步原语显式手写同一调度——预装 k0 块 → 普通 range 循环
{sync → copy(k+1) → MMA(k)} → 末轮 MMA——生成的设备代码消除了全部动态边界谓词，
且未引入任何异步语义。同时以官方布局接口 `make_mma_swizzle_layout(vecSize=4)` 对
Stage2 shared 缓冲做 MMA swizzle 标注，降低 bank conflict。两项均经逐元素对拍
（max_abs=0，与 v432 输出零差异）。

**(g) JIT 编译缓存与 workspace**。`_KERNEL_CACHE` 缓存已编译 kernel（编译
结果，非数据）；`up_logits` workspace 为 scratch 缓冲，每次调用重新计算填充，
符合"建议使用 up_logits 作为中间缓冲区"的题目指引。

### 3.4 per-shape 分派（分派全开）

`hidden ≥ 7000`（case2/3）与 `hidden ≤ 4096`（case1）在 K 循环长度、权重访存
占比上差异显著。v432 对全部 case 统一启用增强 kernel（`_moe_stage1_prefetch` +
`_moe_stage2_fast`），即"分派全开"：case1 实测 -6.8%、case2 -2.9%、case3 -3.7%。
分派依据仅为输入 shape（kernel 特化），不涉及任何结果缓存或阶段区分。

### 4.2 已验证的负结果（同样耗费大量实验，供后来者避坑）

- **`T.Pipelined` num_stages≥2**：MACA 后端无 cp.async，多缓冲只剩同步开销，
  三次独立实验均 -20% 以上；
- **CUDA 流/event 跨kernel重叠**：MACA 运行时不遵守跨流 event 依赖，产生数据
  竞态（4 次复现，含基线同窗 Accepted 的对照）；
- **M256 大 M 块合并 / block_M=64**：寄存器压力/权重重读放大，均负收益；
- **thread=512、bh=32/128、be=64、swizzle panel=8、row 序、k_pack=4**：全部
  实测更慢或编译失败；
- **int8 量化 + 跨调用复用**：违反合规禁令（跨调用缓存），且精度与判据不匹配，
  未采用；
- **手写原生 MFMA（import_source 注入）**：后被官方禁令明确排除，相关历史
  探针全部弃用；
- **官方 TensorCoreIntrinEmitter 严格同步微探针**：128×128×2048 微基准 0.184 ms，
  比同形状朴素 T.gemm（0.242 ms）快 24%，但集成进 MoE 后全部无提分（v487-v490
  四变体：Stage2 5.489 vs 5.473、Stage1 5.537 vs 5.425、双 shared 复用 6.98 vs
  5.47）——证明当前 MoE 已受 global/LDS 搬运主导，MMA 生成质量不是剩余瓶颈
  （emitter 路线终审关闭）。

### 4.3 方法论

所有优化以**同窗口对照**为准（评测机速度存在 ±50% 的档位波动，跨时段分数不可
比）；每次候选先经本地 judge 同构 harness 的**随机 seed 认证**（32 组覆盖三
case + 边界形状，bad=0 才允许上 OJ），再以两次连续 Accepted 确认。

## 5. 创新点总结

1. **A 操作数 shared 化**：MMA 操作数布局从 fragment 迁移到 shared，纯 GEMM
   吞吐 26.8 → 87 TFLOPS（3.2×），是全方案最大单点收益；
2. **无异步指令的 load/MMA 重叠**：利用 MACA 记分板语义的同步寄存器预取
   （up_prefetch / next-K prefetch），在"禁用异步"约束内实现了传统上需要
   cp.async 的拷贝-计算重叠；
3. **编译 pass 开关组合调优**：fast_math / lower_ldgstg_predicated /
   disable_safe_memory_legalize / disable_vectorize_256 的逐 kernel 组合，
   均经逐字节等价性对拍后启用；
4. **per-shape kernel 特化体系**：按输入 shape 选择 kernel 构造器与 pass
   组合，case1 -6.8% 兑现；
5. **系统化合规实验方法**：本地 judge 同构 harness + 随机 seed 认证 + 同窗
   OJ 对照，保证全部结论可复现、可审计。

### 6.1 性能分解与瓶颈分析（实测）

| 阶段 | case1 | case3 | 瓶颈类型 |
|---|---|---|---|
| Stage1（fused Gate+Up） | ≈2.0 ms（72%） | ≈7.1 ms（78%） | MMA 吞吐受限：533 GFLOP（case3）/ 61 TFLOPS 有效 = TileLang 可达上限 87 TFLOPS 的 70% |
| Stage2（Down） | ≈0.8 ms（28%） | ≈2.0 ms（22%） | 访存受限：≈4.3 GB / 2.46 ms ≈ 100% DRAM 带宽 |

带宽利用率：Stage1 ≈45-60%（DRAM 1.44 TB/s 实测峰值），Stage2 接近饱和。
Stage1 的提升受限于 TileLang 可达的 MMA 供给上限（87 TFLOPS，操作数经 shared
的同步供给路径）；Stage2 已贴近带宽上限。**后续 v718/v719 在 E64 形状上通过
terminal-K builder 与 direct emitter 改善了这一供给路径的点效率**（三点分项
79/80→80），说明大 E 形状下 MMA 供给仍有可挖空间。两者性质不同，因此优化手段分别针对
MMA 效率（k_pack / warp 策略 / 寄存器预取）与访存合并（coalesced_width / 满块
epilogue）——与官方答疑推荐的"先判断瓶颈类型再调优"方法论一致（issue 50）。
